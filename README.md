暂时未完善的小项目，支持人和LLM和传统算法对战和算法和算法之间的对战

五子棋 AI 对战平台

| **AI 模型（LLM）** | 走本地 llama.cpp server（OpenAI 兼容接口），模型不可用时自动回退到启发式落子，保证对局不中断 |
| **🧩 传统算法** | **完全不调用模型**的本地搜索引擎，不发任何网络请求，模型服务没启动也能下。难度分四档，**黑白各自设一份** —— 详见 [第九节](#九纯算法玩家不调用模型) |

除了「让模型下棋」，项目还内置两套**可选的「算法 + 模型」协作**实验功能，
用来让「不太会下棋」的本地小模型下得像样一点：

- **传统算法辅助决策**：程序先用轻量算法做侦察（棋型识别、候选点评分、威胁分级），
  把结构化结论写进提示词 —— 详见 [第七节](#七传统算法辅助决策实验性)。
- **混合决策**：在侦察之上再分层放权 —— 必下局面由程序**直接落子**（连模型都不问），
  高警惕局面只给模型 2~3 个点挑，其余不干预 —— 详见 [第八节](#八混合决策实验性)。

> 简单说：**第七、八节是「让模型下得更好」，第九节是「干脆不用模型」，第十节是「算法替人参谋」。**

## 二、环境要求

> 用 [Releases](https://github.com/USERNAME/WuZiQi/releases) 的安装包 / 便携版时，**第 1 条不需要**（Python 运行时已经打进 exe 了），


验证模型服务是否就绪：

```bash
curl http://localhost:10003/v1/models
```

点击页面右上角 **⚙ 设置** 打开设置面板：

| 项目  | 说明  | 默认值 |
| --- | --- | --- |
| 棋盘大小 | 9 / 13 / 15 / 19 路 | 15  |
| 连珠数 | 3 / 4 / 5 子连珠获胜 | 5   |
| 对战模式 | 人机对战 / 机机对战 / 人人对战 | 人机对战 |
| 黑方玩家 | 人类 / AI 模型（LLM）/ 🧩 传统算法 | 人类  |
| 白方玩家 | 人类 / AI 模型（LLM）/ 🧩 传统算法 | AI 模型（LLM） |
| 🧩 传统算法难度 | 简单 / 普通 / 困难 / 极致 —— **黑白各设一份**（在玩家下拉正下方，只有该方是「🧩 传统算法」时才出现） | 普通  |
| AI 模型 | 从 `/api/models` 实时拉取；拉取失败则显示输入框手填。**只对 LLM 玩家有意义** | local-model |
| 模型地址 | llama.cpp server 的地址（含协议与端口）。**纯算法玩家完全不需要** | http://localhost:10003 |
| AI 间隔 | 自动对战/AI 走子间隔，0.3 ~ 5.0 秒 | 1.2s |

点击 **确定并开始新对局** 会调用 `POST /api/new_game` 重置棋盘并立即生效。

> **难度不再是一个全局值。** 每一方各自带自己的档位，所以可以摆出
> 「黑方 简单 算法 vs 白方 困难 算法」这种对局：模式选「机机对战」、两边都设成传统算法、
> 各自挑难度，点「▶ 自动对战」就能直接看出强弱差距。
> 难度还能**边下边改** —— 调完点「仅应用高级设置」，不需要重开对局（详见 [第九节](#九纯算法玩家不调用模型)）。

其他按钮与控件：

- **🔄 重开**：按当前设置重新开局
- **▶ 下一步**：让当前 AI 走一步（人类回合时无效）
- **自动对战 / ⏸ 暂停**：AI 双方按设定间隔自动轮流落子
- **⏪ 悔棋**：回退一步；人机模式下会退回到人类回合，机机模式下退两步
- **🧩 帮我想一步**（状态面板里，只在轮到你落子时可用）：让算法替你算一个落点，
  **只给建议、不自动落子** —— 棋盘上圈出蓝色光圈，你看过之后点「✅ 就下这里」才真的下。
  详见 [第十节](#十让算法帮你想一步人类玩家的参谋)
- **🧠 模型思考**（状态面板里的开关，设置里也有）：即时生效，不用重开对局
  - **关闭**（默认）：直接出坐标，**1~2 秒**一步，棋力一般
  - **开启**：模型先写推理过程再落子，**棋力明显更好，但每步约 1~3 分钟**
- **📄 查看当前提示词**：把「当前轮到的一方」即将发给模型的提示词原文打到日志里；
  若轮到的是**纯算法**玩家，则改为显示「本步不生成提示词」+ 搜索配置
- **🧩 纯算法玩家**：黑白任意一方都能设成「🧩 传统算法」，它**完全不调用模型**
  （不发任何网络请求），每方自带四档难度 —— 详见 [第九节](#九纯算法玩家不调用模型)
- **🤖 模型日志**（棋盘下方）：实时显示每一步的1. **提示词原文**（含模型名、思考开关、棋盘格式、解析/战术开关、采样参数）2. **模型的思考过程**（逐字流式追加，思考模式下就是实时看它推理）3. **最终落子**，并标注这个坐标是「模型直接给出」还是「取自推理末尾」还是「启发式回退」

### 🧪 高级选项（设置面板底部）

这些都可以点 **「仅应用高级设置」** 生效 —— **不重开对局**，边下边调。

| 选项  | 说明  | 默认  |
| --- | --- | --- |
| **棋盘格式** | 提示词里棋盘怎么呈现：`行号+数字` / `逐格标注`（第N行第M列:值）/ `只列棋子`（只列已落子坐标 + 双方清单） | 行号+数字 |
| **思考强度** | 仅「模型思考」开启时生效：低 512 / 中 1024 / 高 2048 / 极高 4096 token | 中   |
| **关思考时也输出解析** | 提示词改为「先定好落子 → 写一行理由 → 最后单独一行给坐标」，日志里能看到它的判断依据 | 关   |
| **战术提示（实验性）** | 程序先算出「谁下一手就能连成 K 子获胜」，把这些点写进提示词 | 关   |
| **传统算法辅助决策（实验性）** | 程序先做棋型识别 + 候选点评分 + 威胁分级，把整份局势报告写进提示词；模型只负责从候选点里挑一个。详见 [第七节](#七传统算法辅助决策实验性) | 关   |
| **混合决策（实验性）** | 在辅助决策之上再分层：**必下局面**由程序直接落子（不再请求模型），**高警惕局面**只给模型 2~5 个候选点挑，其余不干预。详见 [第八节](#八混合决策实验性) | 关   |
| └ 高警惕时最多给几个候选 | 2 ~ 5，默认 3 | 3   |
| └ 强制落子时跳过模型 | 关掉则「仍问一次模型，但答案以程序为准」，可在日志里看模型本来会下哪儿 | 开   |
| **采样参数** | `temperature` / `top_p` / `top_k` / `repeat_penalty`，用 llama.cpp 的原生字段名直接透传 | 0.3 / 0.95 / 40 / 1.1 |

> ⚠️ **坐标编号约定**：提示词里行列都是 **1 起算**（`第1行第1列`），而 `/api/state` 的 `board`
> 和界面上的「内部坐标」都是 **0 起算**。日志里两个都会标出来，例如
> `落在 第8行第7列（内部坐标 7,6）`。解析模型输出时会**先按 1-based 解释，不合法再按 0-based 试一次**，
> 所以模型偶尔按 0 起算也能兜住。

## 五、接口一览（全部 HTTP，无 WebSocket）

| 方法  | 路径  | 说明  |
| --- | --- | --- |
| GET | `/` | 返回 `static/index.html` |
| GET | `/api/state` | 返回当前完整状态 |
| GET | `/api/models` | 代理请求 `{model_base_url}/v1/models`，返回 `{"models": [...]}`；失败返回 `{"models": [], "error": "..."}` |
| GET | `/api/prompt` | 返回当前轮到的一方即将发给模型的提示词原文（含各项高级选项、采样参数与 `hybrid` 决策结果）。轮到**纯算法**玩家时改返回 `{"engine":"algorithm", ...}` + 搜索配置（本步不生成提示词） |
| GET | `/api/analysis` | 返回当前局面的传统算法分析报告（结构化 JSON）；可用 `?player=1\\|2` 指定视角 |
| POST | `/api/hint` | 请求体 `{level?, player?}`，用纯算法替人类**算一个落点**，**只给建议不落子、对状态零副作用**；响应含 `move`/`row1`/`col1`/`depth`/`nodes`/`ms`/`reason`/`changed`（恒 `false`）。详见 [第十节](#十让算法帮你想一步人类玩家的参谋) |
| POST | `/api/new_game` | 请求体 `{size, win_length, mode, players, model_base_url, thinking, thinking_budget, model_params, board_format, analysis, tactics, assist, hybrid, hybrid_hints, hybrid_skip_model, algo_level}`，重置并返回新状态。**难度按玩家写**：`players["1"].level` / `players["2"].level` |
| POST | `/api/thinking` | 请求体 `{enabled}`，开关模型思考模式，**不重置对局** |
| POST | `/api/settings` | 请求体同上表高级选项的任意子集，**在线修改且不重置对局**，下一次 AI 走子立即生效。额外支持 `players_level: {"1":"easy","2":"hard"}` **逐方改算法难度**（`"default"` = 清掉、回归默认档） |
| POST | `/api/move` | 请求体 `{row, col}`，人类落子 |
| POST | `/api/step` | 无请求体，让当前 AI 玩家走一步（非流式，一次性返回最终状态） |
| POST | `/api/step_stream` | 无请求体，**SSE 流式**版 AI 走子：`prompt → notice* → (reasoning\\|content)* → move → state`；轮到纯算法玩家时是 `engine(start) → engine(done) → move → state` |
| POST | `/api/undo` | 悔棋，重置 `winner` / `game_over` |

除 `/api/step_stream`（`text/event-stream`）外，所有响应体都是**同一个完整状态 JSON**（`board` 为完整二维数组）。

`/api/step_stream` 的事件流示例：

```
event: prompt
data: {"prompt":"你在下15×15的连珠棋…","model":"local-model","url":"…","thinking":false,"player":2}

event: reasoning
data: {"delta":"The user wants me to play…"}

event: content
data: {"delta":"4,3"}

event: move
data: {"row":4,"col":3,"player":2,"source":"model","fallback":false,"error":null}

event: state
data: {"state":{ …完整状态… }}
```

`source` 取值：`model`（模型直接给出坐标）／`reasoning`（回答被 token 预算截断，取自推理末尾的结论）／
`algorithm`（混合决策判定必下，由程序直接落子）／`fallback`（模型没给出可用坐标，启发式回退）。

开混合决策且触发「算法强制落子」时，事件流会**跳过 `reasoning` / `content`**，变成：

```
event: prompt
data: {…,"hybrid":{"mode":"forced","rule":"block_unique","move":[7,4],"skip_model":true,"reason":"…"}}

event: notice
data: {"text":"🧮 算法强制落子：…（本步未请求模型）"}

event: move
data: {"row":7,"col":4,"player":2,"source":"algorithm","fallback":false,"error":null}

event: state
data: {"state":{ …完整状态… }}
```

`state.last_decision` 里保留最近一次的决策结果（`mode` / `rule` / `reason` / `points` / `move`），
页面上的「🧠 …」那行读的就是它。

自测示例：

```bash
curl http://127.0.0.1:8123/api/state
curl http://127.0.0.1:8123/api/models
curl -X POST http://127.0.0.1:8123/api/new_game -H "Content-Type: application/json" \
  -d "{\"size\":9,\"win_length\":3,\"mode\":\"ai_vs_ai\"}"
curl -X POST http://127.0.0.1:8123/api/move -H "Content-Type: application/json" -d "{\"row\":7,\"col\":7}"
curl -X POST http://127.0.0.1:8123/api/step
curl -X POST http://127.0.0.1:8123/api/undo
```

## 六、提示词全文 &「为什么它总在乱下」

### 实际发给模型的提示词

在 **🤖 模型日志** 里能看到每一步的原文，也可以 `curl http://127.0.0.1:8123/api/prompt`。
以 9×9 连三子、黑先落 第4行第4列、轮到白棋、`board_format=rows`、战术提示开为例：

```
你在下9×9的连珠棋（Gomoku），连成3子获胜。
棋盘状态用数字表示：0=空 1=黑棋 2=白棋。

当前棋盘（每行左侧是行号，行列都从 1 开始编号）：
行1: 2 0 0 0 0 0 0 0 0
行2: 0 0 0 0 0 0 0 0 0
行3: 0 0 0 0 0 0 0 0 0
行4: 0 0 0 1 1 0 0 0 0
行5: 0 0 0 0 0 0 0 0 0
行6: 0 0 0 0 0 0 0 0 0
行7: 0 0 0 0 0 0 0 0 0
行8: 0 0 0 0 0 0 0 0 0
行9: 0 0 0 0 0 0 0 0 0

【程序算出的战术提示（实验性，请务必参考）】
· 你（白棋(2)）下一手能立刻连成 3 子获胜的位置：无
· 对手（黑棋(1)）下一手能立刻连成 3 子获胜的位置：第4行第3列、第4行第6列
  ⚠️ 如果你不先占住对手的这些点，对手下一手就会赢 —— 优先堵它们。

你是白棋(2)。
注意：只能落在空位上，不能落在已有棋子的位置。
请只输出一个落子坐标，坐标格式统一为：行,列（例如：8,8）
不要输出任何解释、标点或其他文字。
```

**三种棋盘格式**（设置里可切换，`rows` 最紧凑、`cells` 最不易看错、`coords` 信息密度最高）：

```
[rows]   行1: 2 0 0 0 0 0 0 0 0
[coords] 棋盘大小 9×9，当前所有已落子的位置（行列都从 1 开始编号）：
         黑棋(1)：(4,4)、(4,5)
         白棋(2)：(1,1)
         除上述位置外，其余格子都是空的（0）。
[cells]  第1行第1列:2 第1行第2列:0 第1行第3列:0 …（每格都带行列标，15×15 约 2200 字）
```

**开了「输出解析」时**，末尾三段换成：

```
请先在心里定好落子，然后输出两行：
第 1 行：一句不超过 30 字的理由，必须和你最终输出的坐标一致；
第 2 行：只输出坐标，坐标格式统一为：行,列（例如：8,8），不要有任何其他文字。
如果上面的战术提示列出了「必须抢占的点」，请直接从这些点里选。
```

> 相对最初模板的改动：① 原来第一句是「你在下**{N}**子棋」，15 路会写出「你在下15子棋」——
> 这不是真实棋种名，容易把模型带偏，已改成「{N}×{N}的连珠棋（Gomoku），连成{K}子获胜」；
> ② 行列编号从 0 起改成 **1 起**（配合「第N行第M列」的说法）；
> ③ 补了一句「只能落在空位上」（**实测对当前模型无效**，见下）。

### 为什么感觉它在乱下 —— 三条实测原因

1. **思考被截断，答案根本没写出来（最主要原因）**
  这是 Qwen3 系思考模型的通病。实测在 9×9 盘面上：
  
  | 模式  | 结果  |
  | --- | --- |
  | 关思考 + `max_tokens=24` | `finish_reason=stop`，`content='4,3'`，**1~2 秒** ✅ |
  | 开思考 + `max_tokens=1024` | `finish_reason=length`，**全是 `reasoning_content`，`content` 为空** ❌ |
  | 开思考 + `max_tokens=2048` | 还是 `length`，`content` 依然为空 ❌ |
  
  也就是说：**开着思考时，模型压根不会输出「最终答案」这一段。**
  本项目的处理：既然回答被截断，就从推理文本里取坐标，但**取最后一个而不是第一个** ——
  模型的结论总在末尾。实测同一个局面：
  
  - 取第一个坐标 → `(0,0)`（它早期列举候选时提到的一个废点）
  
  - 取末尾坐标 → `(4,2)`（推理最后一句是「(4,2) blocks」之类，正好挡住黑棋）
  
  代价：开思考时每步要约 **1~3 分钟**。所以默认是关思考。
  
2. **提示词只给了棋盘数字，没有任何战术提示**
  "该挡三连""该连自己的子"这些全得靠模型自己推。9×9 这种局面密集的棋盘它还能推对
  （实测黑有 (4,3)(4,4) 它会挡 (4,2)），15×15 稀疏盘面就很容易放弃思考。
  
3. **稀疏棋盘上它会照抄棋盘里唯一那个非零坐标**
  15×15 只落了一颗黑子 (7,7) 时问白棋 —— `max_tokens` 给 24 还是 512、
  加不加「必须选空位」的提示，**6/6 次都稳定输出 `7,7`**（就是黑棋占的位置）。
  这不是应用的 bug，是模型能力上限。此时应用会自动重试一次，仍不行就回退到
  「贴着已有棋子的空位」——老实说这个启发式在稀疏盘面上比模型下得好。
  

### 想让棋力好一点怎么做

按实测效果从强到弱排：

1. **打开 🎯 战术提示（实验性）** —— 这是提升最明显的一条。
  程序先算出「谁下一手就能连成 K 子获胜」，直接写进提示词。
  实测（15×15，黑已在第8行连成四子、白必须堵两端之一，各跑 3 次）：
  
  | 设置  | 堵对次数 |
  | --- | --- |
  | 战术提示 **关** | **0 / 3**（三次都无视四连，去下了别处） |
  | 战术提示 **开** | **3 / 3**（全部下在第8行第7列，正确堵住） |
  
2. **打开 🧠 模型思考**，盯着日志看它推理（它确实会分析棋盘，只是写不完结论）
  
3. **换更小的棋盘 / 更小的连珠数**（9×9 三子棋比 15×15 五子棋容易得多）
  
4. **换一个非思考型、或参数更大的模型**（在 ⚙ 设置里从 `/api/models` 里选）
  
5. **调低温度**（0.2~0.4 适合「只要一个确定答案」的任务）
  

> ⚠️ **「关思考时也输出解析」会略微拖低棋力**，实测同一个必堵局面：
> 关解析 3/3 堵对，开解析 2/3。原因是模型容易「说的和下的不一致」——
> 我见过它分析里写「黑棋在第八行有四子连珠，需立即堵截」，然后坐标输出第6行。
> 已经用更严格的措辞（先定好落子再写理由、理由必须与坐标一致、强制从战术提示里选）把它从 0/3 拉到 2/3，
> 但仍不如关掉。**建议把它当调试/观察功能**，看清它在想什么之后再关掉。

## 七、传统算法辅助决策（实验性）

一句话概括：**程序做侦察，模型做决策。**

打开 **⚙ 设置 → 高级选项 → 🧮 传统算法辅助决策** 后，后端会在每次调用模型之前先跑一遍
传统棋型分析，把结论转成自然语言塞进提示词。模型拿到的就不再是裸棋盘，
而是「有哪些威胁、建议下哪儿、为什么」。

### 分析都算些什么

| 层   | 做什么 | 实现  |
| --- | --- | --- |
| 1 棋型识别 | 每个点沿 4 个方向取长度 2K+1 的窗口，判断中心那一子参与的形状 | `_classify_window` |
| 2 候选点生成 | 只取已有棋子 2 格内的空位（不遍历全盘）；全空则取中心点 | `generate_candidates` |
| 3 候选点评分 | 进攻分（我方下这儿）+ 防守分（对手下这儿）× 0.8，降序取前 15 | `score_candidate` |
| 4 阵型识别 | 一子落下在多个方向同时成型 → 双四 / 四三 / 双三 | `combo_label` |
| 5 威胁分级 | 双方「眠三及以上」的棋型 + 关键点，标 S/A/B/C/D 紧迫度 | `_threat_candidates` |
| 6 关键点 | 双方的「一子即胜」点、最佳进攻点 | `analyze_board` |
| 7 自然语言化 | 整份报告转成提示词里的一个段落 | `render_assist` |

### 棋型判定为什么用「补子试探」

没有为 K=3/4/5 各写一张模式表，而是统一用两个探测问题判定：

1. **补一子就能连成 K 子的点有几个？** 两个 → 活四；一个 → 冲四。
  （活四的定义本来就是「两头都能成五」，所以这个判据是自洽的）
2. **补一子能把它变成活四吗？** 能 → 活三；只能变成冲四 → 眠三。

好处是**对任意连珠数天然成立**；代价是低档棋型（活二/眠二）只能粗判 ——
反正它们分值低，不影响候选点排序。

| 棋型  | 分值  | 紧迫度 |
| --- | --- | --- |
| 五连  | 10,000,000 | S   |
| 活四  | 1,000,000 | S   |
| 冲四  | 100,000 | A   |
| 活三  | 60,000 | B   |
| 眠三  | 1,200 | C   |
| 活二  | 2,000 | D   |
| 眠二  | 200 | D   |

> 分值量级参考常用五子棋评分体系，全部集中在 `PATTERN_SCORES` 一个常量里，想调直接改。
> 注意表里 **眠三(1200) < 活二(2000)** 是照搬参考写法；如果你更认同「眠三强于活二」，把这两个数对调即可。

### 棋型名称会按连珠数自动换算

内部一律用 5 子棋的名字当键，**展示时按 K 换算**：五连 → {K}连、活四 → 活{K-1}、活三 → 活{K-2}……

不这么做的话，9×9 三子棋下会对着**一颗孤子**说「形成活四」，纯属误导。

| K   | 报告里的叫法 |
| --- | --- |
| 5   | 五连 / 活四 / 冲四 / 活三 / 眠三 / 活二 / 眠二 |
| 4   | 4连 / 活三 / 冲三 / 活二 / 眠二 / 活一 / 眠一 |
| 3   | 3连 / 活二 / 冲二 / 活一 / 眠一 |

组合阵型同理：K=5 用习惯叫法（双四 / 四三 / 双三），K≠5 改用实际棋型名拼起来
（三子棋写成「冲二＋活一」），否则换算出来的「二一」根本看不懂。

### 性能

15×15 中期盘面（40 子、80 个候选点）实测：

| 函数  | 耗时  |
| --- | --- |
| `analyze_board` | **约 4 ms** |
| `render_assist` | 约 4 ms |

纯字符串判定函数（`_classify_window` / `_fill_win_points` / `_upgrade_idx`）都加了 `lru_cache` ——
同一盘面上窗口串的重复率极高，命中率相当可观。

### 提示词里长什么样

以「黑在第 8 行连成四子、白必须堵两端」为例（白棋视角）。坐标刻意**全部用「行,列」纯数字（1 起算）**，
与提示词末尾要求的输出格式完全一致，不引入任何解析歧义：

```
【程序用传统算法算出的局势分析报告（供参考，最终由你决定）】
棋盘 15×15，连成 5 子获胜；已下 7 手，你执白棋(2)。
以下坐标一律写成「行,列」且行列都从 1 开始（与棋盘图一致）。

■ 你（白棋(2)）已有的棋型：
· 活三（横）：(9,9)、(9,10)、(9,11)，延伸点 (9,8)、(9,12)（下在这些点可以升级棋型）【紧迫度 B】

■ 对手（黑棋(1)）已有的棋型：
· 活四（横）：(8,6)、(8,7)、(8,8)、(8,9)，你必须堵 (8,5)、(8,10)【紧迫度 S】

■ 关键点：
· 你下一手能立刻获胜的点：无
· ⚠️ 对手下一手就能获胜的点：(8,5)、(8,10) —— 不先占住，你下一手就输了

■ 候选落子点（程序评分降序，共 15 个）：
1. (8,10) 评分 8006000（进攻 6000 / 防守 10000000） · 强防 —— 己方在此形成活二；抢占：对手下这里会形成五连
2. (8,5) 评分 8000000（进攻 0 / 防守 10000000） · 强防 —— 抢占：对手下这里会形成五连
3. (9,8) 评分 1004800（进攻 1000000 / 防守 6000） · 强攻 —— 己方在此形成活四
```

- **强防排在强攻前面是有意的**：堵对手的「一子即胜」防守分是 10,000,000 × 0.8 = 8,000,000，
  天然高过自己做个活四（1,000,000）。符合「先不败再求胜」。
- 打开「关思考时也输出解析」时，提示词末尾会多一句
  「如果上面的局势分析报告给出了候选点，请优先从候选点里选一个」。
- 候选点的「防守分」含义是**对手落在这里会形成什么**，所以文案写成
  「抢占：对手下这里会形成五连」，而不是容易误读的「封堵对手五连」。

### 结构化报告也能单独看

- **页面**：设置面板里的 **📊 查看结构化分析报告** → 概括后打进模型日志（含棋型、关键点、候选点前 8）
- **接口**：`GET /api/analysis`（可加 `?player=1|2` 指定视角）→ 返回完整 JSON，就是上面那段自然语言的数据源

### 它和「🎯 战术提示」的关系

两者可以**各自独立开关**，内容有部分重叠（都会给出一子即胜点）。
同时打开时，提示词里的顺序是 **局势分析报告 → 战术提示 → 任务指令** ——
把短促紧迫的「必须堵这点」放在离任务指令最近的位置，模型更当回事。

### 开关隔离

默认关闭。**关掉时拼出来的提示词与加这个功能之前逐字节一致**。
实测（同一局面）：开 = 2016 字符、关 = 680 字符，报告块 1336 字符，
把报告块从「开」的提示词里削掉后与「关」的提示词**完全相同**。

辅助模块整块套了 `try/except`：它万一抛异常，也只会往提示词里写一行说明，不会中断对局。

## 八、混合决策（实验性）

第七节的辅助决策只做了一件事：**把程序算出来的结论摊给模型，让模型拍板**。
实测棋力提升明显，但有两类局面仍然会翻车，于是补上这一层 ——
核心思路是**分层放权：越确定的局面，程序越强势**。

### 三层放权

| 层级  | 触发条件 | 程序行为 | 理由  |
| --- | --- | --- | --- |
| **算法强制落子** | ① 自己下一手就能连成 K 子；② 对手只剩**唯一**一个「一子即胜」点；③ 对手强威胁的封堵点**只有 1 个** | 程序**直接落子**，不请求模型 | 这类局面的正解是唯一的，模型偶尔会在正解旁边落子，一步走错直接输；程序算得比它准，还省掉一次模型调用 |
| **收敛候选** | 对手有活三一类的强威胁，且封堵点 ≤ 设定上限 | 提示词里**只列这几个点**并追加硬性约束，其余候选点全部撤掉 | 封堵点其实只有 2 个时，把 15 个候选点摊给模型是在**稀释信息**，它容易跑去选一个分数高但无关的点 |
| **不干预** | 其余所有情况 | 完全走第七节那套 | 局面还早，模型的灵活性有价值 |

### 具体例子

```
0 1 1 1 0 1   轮白   →  程序直接下 (8,5) 变成 0 1 1 1 2 1
                        （黑是「跳四」，中间那个空位是唯一正解）
0 1 1 1 1 0 0 轮黑   →  程序直接下 (8,6) 变成 0 1 1 1 1 1 0
                        （自己四连，补任意一端都赢，取靠中心的那个）
0 0 1 1 1 0 0 轮白   →  不代打，只在提示词里给出「(8,2) 或 (8,6)」两个点让模型选
```

### 两个刻意不加限制的地方

- **只有对手的威胁会收敛候选，自己形成活三时不限制。** 防守点是唯一的（堵 A 或堵 B），
  而进攻点常常不是 —— 自己活三时程序建议的两个延伸点，未必比模型看到的「双三」更好，
  此时收窄范围反而丢棋力。
- **对手的封堵点超过上限时直接退回「不干预」。** 比如对手同时在三个方向形成活三
  （封堵点 6 个），硬截成 3 个有可能把正解截掉，不如交给模型。

### 强制落子时「跳过模型」开关

默认**跳过** —— 连一次 HTTP 请求都不发，落子瞬时完成。想观察「模型自己会怎么下」时把它关掉：
此时仍会问一次模型，但**最终采用程序的答案**，日志里会写明模型的落点（未被采用）。

### 模型不听话时会怎样

「收敛候选」是**提示词层面的硬约束，不是强制纠正**。模型如果仍然选了范围外的点，
本次**仍然采用它的落点**（不静默改写模型的判断），但日志里会如实记一条：

```
⚠️ 模型没有遵守「只能从这 2 个点里选」的约束，落在 第1行第9列；本次仍然采用它的落点。
```

这条记录正是这个实验项要观察的东西 —— **硬性约束到底有没有被遵守**。

### 提示词里长什么样

```
■ 候选落子点（程序判定：本局面只有以下 2 个点合理）：
1. (8,2) 程序判定必抢 —— 封堵对手的活三（横方向）
2. (8,6) 程序判定必抢 —— 封堵对手的活三（横方向）

【本轮硬性约束（程序判定，必须遵守）】
程序用传统算法判定：本局面下只有以下 2 个落点是合理的，落在其他任何位置都会立刻陷入劣势：
1. (8,2) —— 封堵对手的活三（横方向）
2. (8,6) —— 封堵对手的活三（横方向）
你必须从这 2 个点里选一个，不得选择其他位置。
```

提示词末尾还会再补一句强调（离模型开始生成的位置最近，约束力最强）。
坐标一律用 **`(行,列)` 纯数字**，不出现中文坐标 —— 避免模型照抄「第N行第M列」
这种写法后解析不出来（现有解析正则认不出中文坐标）。

### 它和其他开关的关系

- 与「🧮 传统算法辅助决策」**各自独立**。只开混合决策、不开完整报告时，
  提示词里只多出那段硬性约束（约 500 字符），不会塞进整份局势报告。
- 两个都关掉时，拼出来的提示词**与加这个功能之前逐字节一致**。

### 性能

| 项目  | 实测  |
| --- | --- |
| 单次决策判定 | **6.4 ms**（15×15 / 60 子） |
| 强制落子那一步 | 不请求模型，落子瞬时完成 |
| 收敛候选那一步 | 正常请求模型（这一步本来就需要它判断） |

## 九、纯算法玩家（不调用模型）

黑白双方都可以设成 **🧩 传统算法**。它是一套**完全自包含的本地搜索引擎**：

- **不发任何 HTTP 请求**，不读模型配置、不拼提示词、不看采样参数
- 模型服务没启动 / 没装 / 地址填错，都不影响它落子
- 走子链路与 LLM 完全分开（`stream_step` 开头就分叉，SSE 事件也只有
  `engine → move → state`，没有 prompt / reasoning / content）

### 怎么用

| 想要的效果 | 怎么设 |
| --- | --- |
| 让算法当你的对手 | 模式「人机对战」，把**白方**设成「🧩 传统算法」 |
| 让算法执黑先行 | 模式「人机对战」，把**黑方**设成「🧩 传统算法」 |
| 算法 vs 算法 | 模式「机机对战」，两边都设「🧩 传统算法」，点「▶ 自动对战」 |
| **比较 LLM 和算法的棋力** | 模式「机机对战」，一边 LLM、一边传统算法，点「▶ 自动对战」看它们互搏 |
| **比较两个难度的强弱（简单 vs 困难）** | 模式「机机对战」，两边都设「🧩 传统算法」，各自挑不同难度，点「▶ 自动对战」 |
| 拿不准时让算法替你参谋 | 轮到你落子时点 **[🧩 帮我想一步](#十让算法帮你想一步人类玩家的参谋)** |

### 难度是「每方一份」，不是全局

难度写在玩家自己身上（`players["1"].level` / `players["2"].level`），所以：

- 黑方可以「简单」、白方可以「困难」，同场对下
- 在设置面板里，难度分段按钮**跟着玩家下拉出现** —— 哪一方选了「🧩 传统算法」，它下面就多出一排四档
- 改动可以**边下边调**：调完点「仅应用高级设置」（走 `POST /api/settings` 的 `players_level`），
  下一步立即生效，不用重开对局
- 后端仍保留 `algo_level` 字段，但它已经降级为**默认档**：某一方**没显式指定**难度时才用它兜底。
  所以老的 `POST /api/settings {"algo_level": "hard"}` 调用依然有效（会影响那些没单独设难度的一方），
  不会出现「改了没反应」。

想改某一方的难度，三种写法都行：

```bash
# ① 开新局时写在 players 里（推荐，界面就是这么发的）
curl -X POST http://127.0.0.1:8123/api/new_game -H "Content-Type: application/json" -d '{
  "size":15,"win_length":5,"mode":"ai_vs_ai",
  "players":{"1":{"type":"algorithm","level":"easy"},
             "2":{"type":"algorithm","level":"hard"}}}'

# ② 不重开对局、在线改（只对「确实是纯算法」的那一方生效，另一方会被忽略）
curl -X POST http://127.0.0.1:8123/api/settings -H "Content-Type: application/json" \
  -d '{"players_level":{"1":"hard","2":"easy"}}'

# ③ 清掉单独设置，让某一方重新跟随默认档
curl -X POST http://127.0.0.1:8123/api/settings -H "Content-Type: application/json" \
  -d '{"players_level":{"2":"default"}}'
```

### 算法构成

| 层   | 做什么 |
| --- | --- |
| **必胜/必堵先手** | 自己一子即胜 → 立刻下；对手只剩唯一必胜点 → 直接占住（这两条不消耗搜索时间） |
| **VCF 连续冲四搜索** | 只走「冲四及以上」的着法，对手只能被动堵 —— 找到就一路逼死。这是「会赢」的关键 |
| **迭代加深 + NegaScout(PVS)** | 从 1 层开始逐层加深，零窗口快速验证 + 失败重搜；结果记进置换表供下一层复用 |
| **Zobrist + 置换表** | 64 位局面哈希，缓存 (深度, 分数, 边界类型, 最佳着法) |
| **杀手走法 + 静态排序** | 置换表着法 → 杀手着法 → 静态评分，走法排序质量直接决定剪枝效率 |
| **增量静态评估** | 每颗子只看自己 4 个方向上的棋型分，落子/悔棋时只重算受影响的那些子（不重扫全盘） |

分支因子的两处刻意压制（既提速又更准）：

- 自己有一子即胜的点 → **只返回它**，不再看别的
- 对手有一子即胜的点 → **只返回这些点**（不堵就直接输，其余走法没有意义）

### 难度档位与实测性能

| 档位  | 目标深度 | 节点预算 | 候选点/层 | VCF 层数 | 实测（15×15 中局，i9-14900HX） |
| --- | --- | --- | --- | --- | --- |
| 简单  | 2   | 300 | 8   | 4   | 2 层 / 43 节点 / ~25 ms |
| 普通  | 4   | 1200 | 10  | 8   | 4 层 / 342 节点 / ~270 ms |
| 困难  | 6   | 4000 | 12  | 12  | 6 层 / 2128 节点 / ~2.2 s |
| 极致 ⚠️ | 8   | 9000 | 14  | 16  | 7 层 / 5932 节点 / ~6.2 s |

**主约束是「节点预算」，不是墙钟时间** —— 这一点是刻意的。
如果拿墙钟时间做截止，同一局面在这台机器上跟在负载高的机器上会停在**不同的迭代层**，
落点就会变，那「同一局面两次调用结果一致」的验收标准就守不住了。
所以迭代加深只认节点数：搜满预算就收手；墙钟时间只当**安全网**
（名义时间 × 4），用来防止病态盘面把浏览器卡死，正常盘面根本碰不到它。

**「3 秒内出招」这条线**：简单 / 普通 / 困难三档都在线内（25 ms / 270 ms / 2.2 s），
覆盖了参考方案要求的「简单 2 层、普通 4 层、困难 6~8 层」。
**只有「极致」会超线**（约 6 秒），所以在界面上标了 ⚠️、并标明它是「分析档」——
它的用途是「我就想看它多算一层」，不适合连下整局。

**关于「深度」要说实话**：参考的算法方案来自 C++ 实现，那里「困难 = 6~8 层」是合理目标；
纯 Python 的节点开销要高两个量级。实测本机的经验值是：
**每多一层，耗时约 ×1.9**（1.4 s → 3.2 s → 6.0 s），
所以「6 层」正好压在 3 秒线附近，**7 层必然超线**。
实际达到的深度会随盘面复杂度浮动，并在**模型日志与状态面板里如实标出**
（例如「深度 6 层 · 2128/4000 个节点 · 2111ms」）。

末层还做一个「预测式加深」：用上一层实际**节点数**估下一层（PVS 节点数一般按 3 倍左右增长），
预测跑不完就直接收手 —— 开了也是白开，只是让你多等一会儿。

### 确定性

同一局面连续调用两次，落点一定相同。做法是**把时间换成节点数**：
搜索的主约束是「节点预算」而不是墙钟时间，全流程无随机数，Zobrist 表用固定种子。
（最初用墙钟做截止，实测同一局面两次调用会落在不同的迭代层、给出不同的点 —— 已改掉。）
悔棋后重新计算的结果也与悔棋前一致（置换表每步重建，不会带脏数据）。

### 量化验证

| 项目  | 结果  |
| --- | --- |
| 一子即胜 | 自己四连时立刻落在端点取胜（0.8 ms） |
| 必堵（你给的 `0 1 1 1 0 1`） | 白方正确落在中间唯一空位 |
| 活三封堵（`0 0 1 1 1 0 0`） | 落在两端之一 |
| 活三延伸 | 自己有活三时优先补成活四 |
| **链式 VCF** | 根局面只有单威胁 → 白被迫堵 → 第二手形成双四（(3,3)/(8,3) 白堵不住）；VCF 搜索 2 个节点、5 ms 内给出必胜手 |
| VCF 不误报 | 安静局面 `vcf` 字段为空 |
| **确定性** | 同一局面连续两次调用落点相同；悔棋重走回同一局面后重算落点也相同 |
| 不调模型 | 用带请求计数的假模型验证：算法回合调用数 **+0**，LLM 回合 **+1**，六步交替全部吻合 |
| 不碰真实棋盘 | 搜索全程在副本上落子/悔棋，真实盘面逐格比对无变化 |

### 它和前两节的实验功能是什么关系

互不干扰，也不必一起开：

- **第七节（算法辅助）/ 第八节（混合决策）**：服务于 **LLM 玩家**，产物是「提示词」。
- **第九节（纯算法玩家）**：本身就是一种**玩家类型**，产物是「落点」，不生成提示词。

所以当轮到的玩家是纯算法时，`/api/prompt` 会如实返回「本步不生成提示词」+ 搜索配置，
而不是硬拼一段没人会用的模型提示词。

## 十、让算法帮你想一步（人类玩家的参谋）

前面三节处理的都是「机器怎么落子」；这一节反过来 —— **替人类做参谋**。

轮到你落子时，状态面板里有一个 **🧩 帮我想一步** 按钮，左边可以选难度：

```
🧩 轮到你时，可以让算法替你算一个落点（只给建议，不自动落子）
[ 困难 ▾ ]  [ 🧩 帮我想一步 ]
```

点下去之后：

1. 算法开始搜索（按钮变「⏳ 计算中…」，期间按钮禁用）
2. 算完在**棋盘上圈出一个蓝色脉冲光圈** —— 是光圈不是棋子，一眼能看出**还没落子**
3. 面板里出现建议框：落点（1 起算的行列）、难度、深度、节点数、耗时，以及**为什么建议下这里**
4. 两个按钮：**✅ 就下这里** / **✖ 忽略**

`✅ 就下这里` 走的还是普通的人类落子接口 `POST /api/move`，
所以落子历史里它和手动点棋盘完全一样（记在「人类」名下，不是「算法」）——
这一点是刻意的：**算法只是给你出主意，这手棋仍然算你下的。**

### 它为什么不会污染对局

`POST /api/hint` 的实现只有一句关键约束：**搜索全程只在棋盘副本上落子/悔棋**。
接口对全局状态没有任何写操作 —— 不落子、不动 `current_player`、不写 `last_move`，
也**不写 `last_engine`**（否则状态面板会把它误显示成「刚走了一手算法」）。
响应里还带一个 `changed` 字段（恒为 `false`）用来自证这一点。

所以你可以对着同一个局面**反复算**：换难度重算、算完反悔、算完自己下别处，都不会留下痕迹。
建议框只存在于前端内存里，**棋盘状态一变（落子/悔棋/重开）就自动作废并清掉光圈**。

### 和「纯算法玩家」的区别

|     | 纯算法玩家（第九节） | 帮我想一步（本节） |
| --- | --- | --- |
| 谁在下棋 | 算法就是这一方的玩家 | **你自己**，算法只是参谋 |
| 落子方式 | 轮到它时自动落 | 你看过建议后点「就下这里」才落 |
| 可用难度 | 该玩家自己的固定档位 | 每次计算都能在下拉里换 |
| 写状态吗 | 是（它真的落子） | **否**（对全局状态零副作用） |
| 可用时机 | 轮到它时 | 轮到你时 |

### 接口

```bash
# 只给建议，不改状态
curl -X POST http://127.0.0.1:8123/api/hint \
  -H "Content-Type: application/json" -d '{"level":"hard"}'
```

```json
{
  "ok": true, "player": 1,
  "row": 5, "col": 8, "row1": 6, "col1": 9,
  "level": "hard", "level_label": "困难", "label": "第6行第9列",
  "depth": 5, "nodes": 1662, "ms": 631, "score": -3600, "vcf": "",
  "reason": "常规搜索 5 层选出评分最高的点",
  "changed": false
}
```

- `level` 可以不传 —— 默认用「当前轮到的那一方自己的难度」；人类没有档位，回落到默认档
- `player` 也可以显式指定（`1`/`2`），用来从另一方视角看这个局面

> ⚠️ 它和纯算法玩家用的是**同一个引擎和同一份节点预算**，所以性能特性完全一致：
> 「极致」档同样会跑到 6 秒左右。想快就选简单/普通。

## 十一、常见问题（FAQ）

**Q0：我就想下棋，不想装 / 不想开模型服务，行不行？**
行。把要当对手的那一方设成 **🧩 传统算法** 即可 —— 它完全不调用模型、不发任何网络请求，
模型服务开不开都无所谓，棋力还比小模型强。
具体设法见 [第九节](#九纯算法玩家不调用模型)。

**Q1：模型服务没有启动怎么办？**
不会崩。`/api/step` 会捕获连接异常，走**回退策略**：从所有空位中挑一个距已有棋子曼哈顿距离最近的位置（全空则下中心点），并把错误写进 `last_error`，前端状态面板会用红色提示 5 秒后自动消失。对局可以继续进行。

**Q2：模型输出解析失败怎么办？**
解析正则 `(\d+)\s*[,，\s]\s*(\d+)` 支持 `7,7`、`7，7`、`7 7`。若模型输出了坐标但越界/该点已有棋子，会继续尝试文本中的下一个坐标对；全部无效时同样走回退策略并记录 `last_error`。

**Q3：端口 8123 被占用怎么办？**
`python main.py` 默认监听 `127.0.0.1:8123`（本机 8000 原本已被其他程序占用，所以换到了 8123）。若 8123 也被占用，换端口即可，无需改代码：

```bash
python main.py 8321                  # 位置参数指定端口
set PORT=8321 && python main.py      # 环境变量指定端口（Windows CMD）
uvicorn main:app --port 8321         # 或直接用 uvicorn
start.bat 8321                       # 一键脚本也支持传端口
```

换端口后访问对应的 `http://127.0.0.1:<端口>`。查看端口占用情况：`netstat -ano | findstr :8123`。

**Q4：界面看不到模型下拉列表？**
说明 `/api/models` 拉取失败或模型服务未启动，此时设置面板会自动切换为**输入框手填**模型名，手填 `local-model` 也能正常提交（多数情况下服务端不严格校验 model 字段）。

**Q5：`uvicorn main:app --reload` 报错找不到 static 目录？**
请确保命令在 `WuZiQi` 目录下执行，且 `static/index.html` 存在。后端用 `__file__` 定位静态目录，与启动位置无关，但 `--reload` 需要能访问到 `main.py`。

**Q6：AI 好像没真正思考，`last_error` 说「输出无法解析」？**
完整分析见上面 **第六节**，简要版：

1. **思考型模型返回空 content**（Qwen3 系最常见）。这类模型默认 `enable_thinking=True`，会把 token 全部花在 `reasoning_content` 上、`content` 留成空串 —— 实测 `max_tokens` 给 24 / 512 / 1024 / 2048 都一样，`finish_reason` 都是 `length`。
  关掉思考模式后 1~2 秒就能拿到坐标；开着思考时后端会退而从**推理末尾**提取坐标（`source=reasoning`），并在面板上说明「答案被截断」。
  若模型服务不认 `chat_template_kwargs` 字段并返回 4xx，会自动改用「提示词末尾追加 `/no_think`」再试一次。
  
2. **模型反复给出已被占用的坐标**。实测在 15×15 这种稀疏棋盘上（全盘只有一颗子），模型会直接照抄棋盘上唯一那个非零坐标。
  后端会重试一次更大的 token 预算，还是解析不出就**自动回退到启发式落子**（贴着已有棋子下），并在状态面板用红字说明原因。
  在 9×9 / 三子棋这种局面密集的棋盘上，模型表现正常（会挡三连、会连自己的子）。
  

> 想换模型：在 **⚙ 设置 → AI 模型** 里从 `/api/models` 拉到的列表里选。本机 10003 上当前是 `qwen3.6-35b-hauhaucs-128k`。

**Q7：日志里看不到东西 / 想看某一步到底发了什么？**
日志是**随点击实时追加**的：点「▶ 下一步」或自己落子后，会依次出现「提示词 → 思考/输出 → 落子」几段。
想在不落子的情况下先看提示词，点右上角 **📄 查看当前提示词** 即可。日志最多保留 120 条，可随时「🗑 清空」。
注意：开思考时推理是逐字流式追加的，看着像卡住其实是模型在写 —— 只要日志长度在涨就是在工作。

**Q8：中途关闭浏览器/刷新页面，会怎样？**
SSE 连接断开后，后端会立刻中止这次模型请求（不会在后台继续烧 GPU）。对局状态保留在服务端内存里，刷新页面会从 `/api/state` 恢复。

**Q9：开了「传统算法辅助决策」后，AI 是不是就变成程序在下棋了？**
不是。程序只负责**侦察和排序**，最终落子仍由模型决定 —— 报告里也明确写了
「上面的候选点是程序算出来的建议，不是命令」。不过要正视一件事：
模型能力较弱时它大概率会直接从候选点里挑，此时棋力就接近「启发式排序」的水平，
而这通常**明显好过模型自由发挥**（实测必堵局面：不给任何提示 0/3 堵对，给了 3/3）。
所以这个功能的定位是**给模型一副拐杖**，不是替换模型。想要真正的棋力应该换成搜索算法
（带 α-β 剪枝的极小化极大），那就不需要 LLM 了。

**Q10：开了「混合决策」，那还需要模型吗？**
需要。混合决策只在**局面已经很确定**时才接管：三类「必下局面」由程序代打，
高警惕局面把候选收窄到 2~3 个让模型选，**其余绝大多数手仍然是模型自由决策**。
换句话说它是**分工**而不是替换 —— 程序负责在关键手不犯错，模型负责在中盘灵活布局。
真正的棋力上限来自搜索算法（带 α-β 剪枝的极小化极大），不是这里。

**Q11：为什么报告说「活四」的点，我数棋子只有两颗 / 三颗？**
这是棋型名称按连珠数换算的结果。报告里的名字是按**当前连珠数 K** 叫的：
三子棋（K=3）里的「活二」约等于五子棋的「活三」（补一子就能形成两个必胜点），
「活一」约等于五子棋的「活二」。换算规则见 [第七节](#七传统算法辅助决策实验性)。
想确认程序到底认出了什么形状，点 **📊 查看结构化分析报告**，
或直接 `curl http://127.0.0.1:8123/api/analysis` 看原始 JSON。

**Q12：日志里已经有「🧮 算法强制落子」，为什么还看到模型在输出？**
两种可能：① 你把「强制落子时跳过模型」关掉了 —— 此时仍会问一次模型，只是**答案以程序为准**，
日志会写明模型本来的落点（未被采用），这正是用来对比观察的；
② 那一步其实是「收敛候选」而不是强制落子 —— 这一步本来就要请求模型。
看提示词日志里的 **混合决策=** 字段即可分辨：`算法强制落子（不经模型）` /
`算法强制落子` / `收敛候选（N 个点）` / `不干预` / `关`。

**Q13：纯算法玩家为什么只显示「深度 5~6 层」，不是说好困难 = 6~8 层吗？**
那是参考方案（C++ 实现）的目标，纯 Python 的节点开销高两个量级。
这里的规则是**「给多少节点就搜多深」**：迭代加深每层完整跑完才更新答案，
节点预算用完就停在上一层，所以实际深度会随盘面复杂度浮动
（中局通常 6 层，安静局面也在 6 层，极致档能到 7 层）。
实测本机**每多一层耗时约 ×1.9**（1.4 s → 3.2 s → 6.0 s），
所以 6 层正好压在「3 秒内出招」这条线上，7 层必然超线 ——
这就是「困难」到 6 层、「极致」才到 7 层且要标 ⚠️ 的原因。
实际深度和节点数都会如实写在模型日志和状态面板里，不会假装算到了。

用「节点」而不是「时间」做截止是刻意的：拿墙钟做截止，同一局面在不同机器负载下
会停在不同的迭代层、给出不同的点，「同一局面两次结果一致」就守不住了（见第九节）。
嫌慢就把难度调低，嫌弱就调高。

**Q14：纯算法玩家走子时，日志里为什么没有「提示词」？**
因为它本来就不发提示词 —— 它直接在本地搜索，链路里根本没有模型这一环。
日志会显示「🧩 纯算法开始搜索 → 深度/节点/耗时 → 落子」，
SSE 事件流也只有 `engine → move → state`。同理，这几步**不会**产生
`last_error`、也**不会**因为你没开模型服务而回退。

**Q15：我想让黑方用简单算法、白方用困难算法，怎么设？**
可以，难度是**每方一份**的。设置面板里，哪一方选了「🧩 传统算法」，
它下拉框下面就会多出一排四档按钮，两边各挑各的。想直接看差距就用
「机机对战」+ 双方都设传统算法 + 各自挑难度 + 点「▶ 自动对战」。
接口侧写在 `players` 里即可：

```bash
curl -X POST http://127.0.0.1:8123/api/new_game -H "Content-Type: application/json" -d '{
  "size":15,"win_length":5,"mode":"ai_vs_ai",
  "players":{"1":{"type":"algorithm","level":"easy"},
             "2":{"type":"algorithm","level":"hard"}}}'
```

界面上的「确定并开始新对局」和「仅应用高级设置」都会带上这两个难度，
所以**改难度不用重开对局**（后者走 `/api/settings` 的 `players_level`）。
详见 [第九节](#九纯算法玩家不调用模型)。

**Q16：改难度时我只改了一方，另一方会被一起改掉吗？**
不会。`/api/settings` 的 `players_level` 是**逐方**下发的，
而且**只对「确实是纯算法」的那一方生效** —— 给人类或 LLM 那一方传难度会被直接忽略，
不会给它塞上一个无意义的 `level`。

**Q17：「帮我想一步」点完之后，是不是就自动替我下了？**
没有。它**只给建议**：棋盘上圈一个蓝色光圈、面板里给一行理由，
点「✅ 就下这里」才真的落子，你也可以点「✖ 忽略」或者直接在别处下。
整个过程对后端状态**零副作用**（`POST /api/hint` 只在棋盘副本上搜索，
不写 `last_engine`、不改 `current_player`），所以同一个局面可以反复算、换难度再算。
详见 [第十节](#十让算法帮你想一步人类玩家的参谋)。

**Q18：「帮我想一步」算出来的建议，会记成「算法下的」吗？**
不会。你点「就下这里」走的是普通的人类落子接口 `POST /api/move`，
落子历史里记的是**人类**。这是刻意的 —— 算法在这条链路里只是参谋，
这手棋算你下的，输赢都算你的。

## 十二、打包与发布

### 打包链路

```
main.py + static/  ──PyInstaller──►  dist\WuZiQi\ (exe + _internal\)
                                          │
                                          ├─►  portable zip（免安装版）
                                          └──Inno Setup──►  WuZiQi-1.0.0-Setup.exe（安装包）
```

### 一键打包

**双击 `build.bat`**，它会自动：建/复用 `.buildenv` 虚拟环境 → 装依赖 → 生成图标 →
PyInstaller 打包 → 打便携版 zip → 调用 Inno Setup 编译安装包。
产物全部落在 `release\` 目录：

| 文件  | 用途  |
| --- | --- |
| `WuZiQi-1.0.0-Setup.exe` | 安装版，上传到 GitHub Releases |
| `WuZiQi-1.0.0-portable-win64.zip` | 免安装版，上传到 GitHub Releases |

### 只重新打 exe

```bash
python -m venv .buildenv
.buildenv\Scripts\python.exe -m pip install -r requirements.txt pyinstaller
.buildenv\Scripts\python.exe -m PyInstaller WuZiQi.spec --noconfirm
```

> `WuZiQi.spec` 里已经固化了三件容易踩坑的事：静态资源 `static\` 一并拷进 `_internal\`；
> uvicorn 的动态导入模块（`uvicorn.loops.auto` / `uvicorn.protocols.http.auto` / …）作为 hiddenimports 显式列出；
> 图标与版本信息带上。**改完不要手动删 spec，改 spec 就好。**

### 在 GUI 里编译安装包

1. 双击 `"D:\innosetup\Inno Setup 7\ISIDE.exe"`
2. `File → Open` 打开 `installer\WuZiQi.iss`
3. 按 `Ctrl+F9`（或菜单 `Build → Compile`）
4. 底部 `Compiler Output` 出现 `Successful compile` 即成功，
  安装包在 `installer\Output\WuZiQi-1.0.0-Setup.exe`

> `installer\WuZiQi.iss` 带 **UTF-8 BOM** —— 用记事本另存时务必继续选 UTF-8，
> 否则中文应用名会变成乱码。

编译前请确认 `dist\WuZiQi\` 是**最新**的（先跑 `build.bat` 或 PyInstaller），
否则会把旧版本打进安装包。

### 发布到 GitHub

```bash
# 首次：设置身份 + 初始化仓库
git config --global user.name  "你的名字"
git config --global user.email "你的邮箱"
git init
git add .
git commit -m "五子棋 AI 对战平台 v1.0.0"
git branch -M main
git remote add origin https://github.com/USERNAME/WuZiQi.git
git push -u origin main
```

然后把 `release\` 里的两个文件拖到 GitHub 的 **Releases → Draft a new release** 里，Tag 填 `v1.0.0`。

记得把本文件里的 `USERNAME`（共 3 处）和 `installer\WuZiQi.iss` 顶部的
`MyAppPublisher` / `MyAppURL` 改成你自己的信息。
